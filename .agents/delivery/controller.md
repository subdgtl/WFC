# Independent delivery

This procedure supports a controller in either Codex Cloud or Claude Code cloud. Start delivery only when the owner asks. Preparing or merging these instructions does not start a controller, create a schedule, change a running controller, or grant deployment permission.

## Before starting

Read the repository instructions, this file, `policy.json`, and the repository-specific skill. Preserve owner approval, platform acceptance and deployment restrictions. One controller owns a repository at a time. Record that claim on GitHub with its provider session identifier and the repository's current main commit. Inspect existing claims, branches and open pull requests before starting; coordinate an existing controller rather than taking its work.

Use subscription sign-in. Never copy sign-in files or provider keys between machines. A Codex command running inside a Claude machine still shares that machine. A worktree, subprocess or subagent gives code isolation, not additional hardware. Heavy work goes to a new provider cloud task or session, or to a separate physical machine. An unavailable native platform remains unavailable; Linux compilation does not establish Rhino, Windows, Apple, hardware or production acceptance.

Validate setup on each worker before giving it work. Record its provider session identifier, actual model and effort, platform, tool versions and machine fingerprint. A cloud environment identifier names a configuration and is not proof of a different machine. Keep the setup on the worker independent of integration. If required setup still blocks an integration, include that time in the five-minute allowance.

## Implementation and integration

1. Select an open, implementable issue with completed dependencies. Inspect its assignee, claim comments, branches, worktrees and pull requests. Claim it once, naming the implementer and branch. Use a separate branch and checkout for each unit. Preserve the repository's existing issue sections, labels and owner decisions. Record questions as blocked issues with the exact question.
2. Assign Codex and Claude work through their supported providers. Both controllers can use both implementers; the owner may choose a provider for a particular run. Keep existing explicit provider preferences. Return commits and check evidence, not a statement of completion. Do not let a worker merge, tag, deploy or make a second ownership claim.
3. Determine compilation or type checks, lint, and focused tests that cover the actual change. Include direct geometry, permissions and data-integrity checks where relevant. A syntax check does not replace behavior tests. Record the chosen checks and why they cover the change. Unknown paths or missing coverage fail explicitly.
4. All required automated checks for one integration share one persisted allowance of at most **300 seconds total**. Use `runtime.py integration-checks`, including the reviewed focused plan where the repository adapter requires it. Keep the same integration identifier across commands, corrections and retries. Starting another process, renaming a gate, restarting the controller, or changing a command must not reset the allowance. Exhaustion is a failure; it is never a pass. Move costly full coverage to independent verification while retaining meaningful focused checks. If no adequate focused checks fit, narrow the issue or improve the check and report the blockage.
   A cloud controller first uses `reserve-integration`, exports its checkpoint, and publishes the entire checkpoint through the existing durable adapter. Only after actual publication succeeds does it call `confirm-reservation` with that checkpoint and its storage receipt, then `integration-checks --reservation` with the exact reserved candidate and plan. Publication and waiting consume the original allowance. Publish the settled checkpoint afterward. Restored reservations cannot execute again; a failed publication must never be confirmed. The synchronous path is for controller state that already survives process or machine loss. See `README.md` for the commands.
5. Commit verified increments, push a branch, and open a pull request. Review the same commit independently with **GPT-6 Astra at ultra effort** and **Claude Code Opus 5.5 at max effort**. Require the actual model identifiers `gpt-6-astra` and `claude-opus-5-5` in provider evidence. An alias, requested model, or another GPT agent is not evidence of an Opus review. Read-only reviews may run concurrently on independent machines. Reviewers inspect the artifact and test coverage, including whether the change increases blocking checks.
6. Send all findings to the same implementer. Reviewers that requested changes check their own findings on the corrected commit. Preserve any stricter existing correction limit; otherwise allow one correction and one further correction. Unresolved findings wait for resolution. Post both reviews, correction verification, implementer, host-run checks and exact commands/results on the pull request.
7. Integrate current main, resolve conflicts, apply the repository's version policy and regenerate its lockfiles using the normal tools. Repeat affected focused checks within the same integration allowance. Confirm the committed tree equals the tested candidate tree. Hold for owner approval where required. Squash-merge through a pull request with its expected head commit, except where the repository explicitly requires a different merge method. Verify main's resulting tree equals the reviewed and tested tree. Never push implementation directly to main.
8. Enqueue the exact resulting main commit for full verification. Continue implementing immediately. Do not wait for the full gate before taking another issue. A confirmed build failure stops further merges until its repair merges; other full failures create repair work and do not stop merges.

## Independent full verification

Use `runtime.py enqueue` after every merge and on a recurring main inspection. For each repository keep one running immutable commit and only the newest pending descendant. Never cancel a running gate merely because main advanced. Intermediate commits need no full run or release tag.

The controller claims a verification job and exports its request. A separate machine checks out that exact commit and runs `runtime.py run-job` with every required platform check, environment probe and artifact requirement. Return the entire result directory: receipt, command logs, environment evidence and artifacts. The controller uses `accept-result`; a summary, green icon, requested model, timeout or unavailable tool cannot stand in for that evidence. Existing gates remain complete. Do not delete suites, convert required checks to optional, suppress failures or skip unavailable platforms to produce a pass.

Poll or receive the supported provider completion event while implementation continues. Missing sessions, dead workers and expired environments need a recorded recovery decision. Do not automatically steal a running lease or restart a possibly live job. Checkpoint controller state after each ownership, budget, queue, dispatch, result and repair transition to durable storage available after the controller machine disappears. Restore it before resuming; preserve consumed allowances and running claims. SQLite is local state, never a database shared directly across machines. A provider conversation summary is not the durable queue.

Full failures create a repair outbox entry. Publish one deduplicated GitHub repair issue per unresolved failure, using the repository's required sections and priority labels. Include tested commit, platform, exact command, failed stage and retained log location. Link the issue back with `repair-link`; reconcile existing issues on restart before publishing. Do not create another issue every time the same failure recurs. Resolve a failure only on actual repair evidence.

After the running job ends, claim the latest pending commit. Repeat. Schedule a main inspection at least hourly and on every merge, through the provider's supported cloud scheduler. A local fallback can import the cloud controller's checkpoint and run `serve` on a dedicated verification machine. `serve` consumes the existing queue; it does not fetch main or create a schedule. The cloud controller still enqueues each merge and performs the scheduled inspection. The local process survives only while its machine runs. A schedule described in this file is not an installed schedule. Record the actual schedule identifier, controller identity, heartbeat and recovery path when the owner starts it. Do not add GitHub Actions.

## Releases

`runtime.py release-check` requires complete passing receipts for the exact main commit, tree, policy, suite inventory, platform coverage and artifacts. Use the existing repository release guard as well. Honor explicit release blockers and owner/native acceptance. A build-only profile must not be presented as behavioral acceptance. Distribution archives require source verification and matching artifact provenance.

An annotated version tag belongs only on that exact verified commit. Never move or reuse a tag. Skip unverified intermediate versions. Build and deploy from the tested tree and matching artifacts; an advancing main branch does not authorize deploying its newer head. Preserve existing approvals, backup, signing, credential and production restrictions. This rollout installs no schedule, starts no delivery, and performs no tag, release or deployment.

## Provider dispatch

Use `cloud.py` to prepare a request and supported command for each provider. Codex uses `codex cloud exec --env <configured-environment> --branch <published-branch> <prompt>`; inspect task status and retrieve its returned evidence. Claude Code cloud can use its `claude-code-remote` connector's `create_session` with `source_url`, `source_revision`, `outcome_branch`, `model`, `environment_id`, `prompt` and `title`, then `get_session`, result events and messages. The command-line alternative is `claude --cloud <prompt>` from the appropriate published repository branch. It creates a new session; `claude -p --cloud <session-id>` sends a follow-up to an existing one.

Use the real connector schema exposed in the running environment. Do not invent HTTP endpoints, tools, environment identifiers, model options or a programmatic result API. Cloud creation needs the configured account, repository access and environment. Codex cloud command-line model overrides are not verified by the installed command's help: confirm the actual cloud model or select it in the supported interface before accepting a review. Failure to configure a provider is an explicit unavailable capability, not a reason to run heavy work on the controller or change providers silently.
